# 先手部、后身体与 batch=32：方案及验收状态

2026-10-14。目标保持100帧置信度压缩、100轮、逐训练批次warmup+余弦学习率、随机初始化、强制torch.compile。

执行顺序：左手共享CTR-GCN编码及节点池化 → 右手共享CTR-GCN编码及节点池化 → 五点头部朝向编码 → 身体前4块 → 左右手特征分别注入对应手腕、头部特征注入鼻点位置 → 身体后6块 → 分类。头部编码可在身体计算前生成，投影与融合仍在中间注入位置进行。各阶段分开编译，最终分类损失统一反向传播，不冻结或缓存随机手部编码器的输出。

目标为真实视频batch=32，每批2个人物槽位，身体和单只手编码时的人物维批次为64。左右手依次处理，避免将两只手合并成128的编码批次。每32段视频恰好一次optimizer更新和一次学习率进度推进。

仅改变执行顺序不能消除手部反向传播需要保存的激活。若真实batch=32显存不足，下一步优先设计手部激活检查点，在反向时重算；需要避免重算重复更新masked BatchNorm的running statistics，并验证梯度及缓存更新次数。该方案尚未实现和验收。代价是额外计算及可能降低吞吐。不能detach、no_grad或离线缓存手部输出，否则会切断从最终分类损失到随机初始化手部编码器的训练。

内部微批次只用于当前编译诊断。尽管optimizer batch仍为32，PointBatchNorm按每次调用单独统计并更新running buffers，因此不能称为与真实batch=32等价。进一步改用梯度累积也属于不同训练协议，不能直接替代当前每训练批次一次更新的约定。

CUDA实测环境：RTX 5090 32GB、PyTorch 2.8.0+cu128、Triton 3.4.0。手部第1块在实际预处理构造的输入上，人物batch=1和64均通过真实编译前向和反向；第2块在两种批次上均出现PassManager::run failed。完整训练尚未完成首批，不能据此判断完整模型batch=32的峰值显存或吞吐。减小微批次、连续化张量及改变TF32设置尚未解决问题；不得把这些诊断假设描述为根因或已修复。
